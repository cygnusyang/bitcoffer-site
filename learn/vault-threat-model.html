What does a local vault protect against, and what does it not?

It protects the data at rest: a stolen disk, a copied file, a backup on the wrong drive. It does not protect an unlocked session, a machine running malware as you, or you forgetting the one thing you cannot reset. Written down because a security page that lists only the first column is a sales page.

How the at-rest protection actually works

Four layers, and the design choices in each one explain the limits in the table above:

  1. Key derivation: Argon2id. The master password is stretched with a memory-hard function, so guessing is expensive in RAM as well as time. The parameters live in the vault header, which means a vault can be re-keyed with stronger settings later without the file format changing.
  2. Encryption: AEAD. The vault body is sealed with an authenticated cipher (XChaCha20-Poly1305), so a modified file fails to open rather than opening to garbage. Bitcoffer routes all sealing through a single crypto entry point rather than letting each module pick its own.
  3. The master password is not stored. There is no verifier to steal and no "hint" field. A wrong password is simply a key that produces an authentication failure.
  4. Recovery is a wrapped key, not a backdoor. A recovery code derives a separate key that wraps the vault's data key with AES-256-GCM. That is why recovery works without the password, and why losing both is unrecoverable: the code is the second key, not a request to a support desk.

What this adds up to: an attacker with your disk gets a file that costs real money to attack, and an attacker who also gets your recovery code gets everything. Both statements are load-bearing.

The four cases it cannot cover

1. An unlocked session

Once you unlock, the data key is in memory and the app will decrypt on request. Anything that can ask the app — a script, a malicious binary, a compromised editor plugin running as you — can get what it asks for. Touch ID shortens the window; it does not close it. This is the boundary every local password manager shares, and any claim to have solved it deserves hard evidence before you believe it.

2. Malware that targets the clipboard or the screen

Copy a password, and it is in the clipboard where any process can read it. Look at a password while someone records the screen and it is in a video. A vault protects storage; it cannot protect a value after you have deliberately exposed it to the system.

3. Physical access with cooperation

If someone has your machine and can make you unlock it, encryption is not the relevant control. The relevant control is that the vault is not the only copy of anything you cannot afford to lose — see the next section.

4. Forgotten credentials with no recovery code

This is the failure that actually happens most often, and it is a design choice rather than a flaw. A vendor who can reset your password can also be compelled to, and can also be breached. Choose which risk you want; do not expect both.

Why this decides your backup plan

The threat you are actually worried about tells you what to back up, where to put it, and how often — and doing it the other way round produces a backup that protects against the wrong thing:

If your real worry is…Then…
Device theft or disk failureAn encrypted backup kept off the machine, restored once to prove it works
Ransomware or malware on your MacA backup the malware cannot reach — offline or on a different account, not a folder the same process can encrypt
Forgetting the master passwordA recovery code stored somewhere you can still reach if the Mac is gone
Accidentally deleting an itemVersioned backups with a retention window, not a single overwritable copy

Notice that three of those four require the backup to live somewhere other than the vault's own directory. A backup inside the same folder as the vault is a second copy, not a backup.

The claim you can check, and the one you cannot

Two different assertions get bundled together in security marketing, and separating them is most of the value of a threat model:

  • Checkable: the app cannot open a server socket, opens no connection while idle, and links no third-party network code. Four commands, five minutes, and the result is either consistent or it is not.
  • Not checkable by you: that the binary was built from the source the developer describes. No user-accessible command answers that. Bitcoffer's source is private, and the site offers a source audit by email instead — weaker than a public repository, and worth saying so plainly.

A threat model that does not draw that line is not a threat model. It is reassurance, and reassurance is what you get from the products that need it most.
