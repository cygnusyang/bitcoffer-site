How do I verify a password manager really does not talk to the internet?

You do not verify the promise. You verify the binary: what it is allowed to do, what it links against, what it opens while it runs, and what its dependency graph contains. Four checks, four different questions — and each one has a failure mode that a marketing page will never mention.

Updated 2026-11-17 · by cygnus, the developer of Bitcoffer

Why "no cloud" is usually unfalsifiable

Almost every password manager says your data stays private. Very few of them say something you can disprove. "Encrypted in transit and at rest" is true of a service that reads your vault. "Zero knowledge" is a claim about a protocol you cannot inspect from outside. The words are chosen so that no command you run will contradict them.

A checkable claim has a different shape: this app cannot open a listening socket, and it opens no connection while idle — here is the command, run it yourself. That claim can fail. Run lsof and see a connection you cannot explain, and the claim is dead. That is what makes it worth reading.

There is no shortcut here. Trust in a password manager is not established by a better-written privacy policy; it is established by a smaller number of things you have to take on faith. Below, four checks and — more usefully — what each one fails to cover.

Check 1: what the app is permitted to do

Every macOS app that touches the network needs an entitlement for it. The entitlements are inside the signed bundle, so you can read them without the source:

codesign -d --entitlements - /Applications/Bitcoffer.app

What you are looking for, on any app making this claim:

  • com.apple.security.app-sandbox is true. Without the sandbox the entitlement list is advisory — a signed app outside the sandbox can do whatever its user can do.
  • com.apple.security.network.server is absent. This is the one that matters most and is checked least. A client socket lets an app call out; a server socket lets something call in. A password manager never needs the second one, and if it is present, "local" means something different from what you assumed.
  • At most com.apple.security.network.client appears, and you know why. An update check needs a client socket. If that entitlement exists, the honest version of the claim is "no network except one host I can name", not "no network".

The failure mode of this check: entitlements constrain what the sandboxed process may do. They say nothing about a second process the app launches — a helper tool with its own entitlements. If you are auditing seriously, list the helpers too: ls /Applications/Bitcoffer.app/Contents/ and check each binary in MacOS/ and Helpers/ the same way.

Check 2: what the binary links against

otool -L /Applications/Bitcoffer.app/Contents/MacOS/Bitcoffer

This lists the dynamic libraries. The question it answers is not "does the app have network code" — it always does, in some form — but "did the developer pull in a full HTTP stack they do not need".

Three outcomes, and readers routinely misread the second one:

What you seeWhat it means
No network library at allStrongest outcome, and rare — it means even the update check goes through something unusual
CFNetwork only, no Network.frameworkExpected for a macOS app whose only outbound code is an update check through URLSession. CFNetwork is the system framework underneath it; its presence is not evidence of extra behaviour
libcurl, libssl, a vendored reqwest-style stackSomeone linked a general-purpose HTTP client. It is not proof of malice, but it is a much larger surface than an update check needs

Bitcoffer lands in the second row deliberately, and the distinction is worth stating precisely because it is the kind of detail a vendor usually blurs: CFNetwork present, Network.framework absent, no third-party network code. The app's own self-certification page prints these commands and says the same thing.

The failure mode here: otool -L shows what is linked, not what is called. A framework that is linked and never used looks identical to one that is used constantly.

Check 3: what it actually opens while running

This is the only check that observes behaviour rather than capability, and it is the one people skip because it requires the app to be running.

pgrep -x Bitcoffer
lsof -nP -iTCP -iUDP -a -p <pid>

The -a flag is not optional. Without it, lsof treats -i and -p as alternatives and prints every network connection on the machine, which is how a lot of hand-written audits accidentally "prove" that an app is calling out when it is not.

An empty result means no TCP or UDP socket belongs to that process. Two honest caveats:

  • Idle is not the same as never. An app that checks for updates on request will show a connection while the check runs. The claim to test is the steady state: launch it, leave it alone, and look again after a minute.
  • A moment of observation is a sample, not a proof. A connection that lasts 200 ms and happens once a day can be missed by any single lsof. This is why check 4 exists.

Check 4: what the code is allowed to depend on

Static and dynamic checks see the shipped binary. The dependency graph sees the intent, and it is the one check that can fail loudly in CI rather than quietly in production:

cd core && cargo tree --workspace -e normal

For a Rust core the question is narrow and answerable: does anything in the normal dependency set pull in an HTTP client or an async runtime with networking enabled? reqwest, hyper, or tokio with its net feature are the usual suspects. A CI job can assert their absence on every commit, which is a stronger guarantee than a review that happened once:

./tools/check_no_network.sh

The failure mode: a dependency graph is only as good as the code that builds it. Feature flags can enable networking in a crate you would not expect, and a transitive dependency can change behaviour in a patch release. This check tells you what the project intends, not what a specific build did.

What none of the four checks prove

They do not prove that the binary you downloaded was built from the source the developer describes. A signed, notarized, correctly-entitled app can still contain code its author never published, and no command available to a user distinguishes that from an honest build.

That gap is closed by only two things, and it is worth being blunt about which one you have:

  • Reproducible builds, where anyone can rebuild from source and compare hashes. Very few consumer apps do this, because it is genuinely hard.
  • Reading the source yourself, under whatever access the vendor grants. Bitcoffer's source is private; the site offers a source audit by email instead. That is a weaker guarantee than a public repository, and calling it anything else would be dishonest.

So the realistic conclusion for any local-first password manager is: the four checks shrink what you have to trust from "our servers are secure" to "this developer built what they said they built". That is a real improvement and it is not the same as proof. Anyone who tells you they have the proof is selling something.

Run all four in about five minutes

APP=/Applications/Bitcoffer.app
codesign -d --entitlements - "$APP" 2>&1 | grep -i network
otool -L "$APP/Contents/MacOS/Bitcoffer" | grep -iE 'curl|ssl|network'
open -a Bitcoffer && sleep 5
lsof -nP -iTCP -iUDP -a -p "$(pgrep -x Bitcoffer)"

Expected output for Bitcoffer: one network.client entitlement and no network.server; no third-party network library (system CFNetwork is expected); and an empty lsof while the app sits idle. If any line disagrees with that, the claim is wrong — not "probably still fine".
